# Upscaler and frame-generation hook

The native renderer (`KARTRECOMP_NATIVE_GPU=native`) has a hook for temporal upscalers and frame generators.
The game binary carries no third-party SDK code: backends are shared libraries loaded at run time.

## Use

```
KARTRECOMP_UPSCALER=passthrough            built in
KARTRECOMP_UPSCALER=fsr3                   loads plugins/libkr_upscaler_fsr3.so (relative to local/game)
KARTRECOMP_UPSCALER_LIB=/path/to/lib.so    explicit library
KARTRECOMP_JITTER=1                        sub-pixel camera jitter (also fixed:<px> for tests)
```

## Where the hook runs

`RunUpscalerHook()` in `vk_shadow_backend.cpp`: at the first half-size, no-depth render pass after the full-size HDR scene
(the start of the game's bloom chain). Scene colour = the last full-size B10G11R11 target written before it; depth =
the last full-size depth target; the output replaces the scene colour for everything after. HUD, menus and the bloom/tonemap
chain are never given to the upscaler. All images are in `VK_IMAGE_LAYOUT_GENERAL`, the command buffer is recording and
outside a render pass.

## Plugin ABI

See `suyu_cmd/native_gpu/upscaler.h` in the fork (patch 0001): `KrUpscalerApi { abi_version, name, create, configure,
dispatch, destroy }` and `KrUpscalerFrame` (colour, depth, motion, output images and views, render and output sizes,
jitter in pixels, delta time, camera near/far/fov, sharpness, exposure, reset, frame index). Export
`const KrUpscalerApi* kr_upscaler_get_api(void)`. A plugin creates its own FidelityFX/NGX context in `create` from the
Vulkan instance, device and queue it is given.

### FSR 1 and render scale (2026-10-21)

- Pick Upscaler = FSR 1 and lower Render scale: the game draws at the smaller size, then the window image goes through EASU
  (edge-adaptive upscale) to the output size, optionally RCAS (sharpening), and is copied into the swapchain image. It
  needs no motion vectors or jitter, works on any GPU, and is the lowest-risk path to real fps gains.
- Render scale: up_scale / 2^down_shift in `Settings::values.resolution_info` (100 = 1/1, 67 = 43/64, 58 = 37/64, 50 = 1/2,
  33 = 21/64). Screen-size render targets (`guest_height > 288`, one level) are destroyed and recreated at the new size
  on next use; their old contents are not kept, so the first frame after a change can show a flash.
  `KARTRECOMP_NATIVE_NOSCALE` still works for tests but the overlay's scale overrides it.
- Menu rows persist in `user/config/kartrecomp_overlay.ini` (upscaler, jitter, quality, sharpness, present,
  speed_percent, fps). The speed limit option order is now ascending.
- Tested with scripted menu presses and final-image captures: FSR 1 at 100% and 67% looked clean. Not yet measured: the
  actual fps gain at 1440p, and comparison against the plain blit.

### Output resolution, render scale and the upscale point (2026-10-21)

- Output resolution is a pixel height (720, 1080, 1440, 2160), not a multiplier: `out_scale = height / 1080`.
  `KARTRECOMP_NATIVE_HEIGHT=<h>` (the launcher sets it) is the default; the overlay's "Output resolution" row overrides it.
- The 3D render scale is a share of that: `scene_scale = out_scale * ratio`. The ratios 2/3, 7/12, 1/2 and 1/3 give
  whole pixels at 1080p; the earlier steps (43/64, 37/64) did not, which shifted the picture a little per setting.
- With a render scale on, every frame that has a 3D scene and a recognisable HUD pass is split in two:
  1. passes up to the tonemap draw at `scene_scale` (screen-size render targets follow `cur_scale`; a target whose
     scale no longer matches is recreated in place on its next use, `ResizeImageScale`);
  2. at the first HUD pass (the second pass that draws into the tonemap's RGB10A2 full-size image, or the pass that
     reads it into the window image), the tonemapped 3D image is upscaled into `up_image` (output size) and the HUD and
     final pass see `up_image` in its place (`GetImage` alias), at `out_scale`.
  Frames without a found HUD pass but with a 3D scene render whole at `scene_scale` and the present step upscales them;
  frames without a 3D scene (menus) render whole at the output size.
- With the render scale off the whole frame renders at the output size and FSR 1, if selected, runs at present time.
- Inputs for a future temporal upscaler or frame generator: the tonemapped colour at the scene scale (LDR), the scene
  depth at the scene scale, zero motion vectors (to do) and the jitter in render pixels; output at the output size,
  HUD not included. A pre-tonemap (HDR) hook point would be a further option for FSR 3 / DLSS quality.
- Saved in `user/config/kartrecomp_overlay.ini`: upscaler, jitter, quality, resolution, sharpness, present,
  speed_percent, fps.

## Camera motion vectors (2026-10-21)

The hook (`KARTRECOMP_UPSCALER=...` or the overlay's Upscaler row, with the 3D render scale on) now gets a real RG16F motion image
(render pixels, prev = cur + mv) instead of zeros, and `reset` = 1 when there was no camera last frame.

- **Finding the camera:** the game keeps the main view-projection in a vertex-stage constant block of the scene passes (a block
  of 176/192/224 bytes: view 3x4, then view-projection rows, then the projection's inverse in another block). `FindCamera` scans
  those blocks (first 1 KB, only for depth-target passes at screen size, once per frame) for four consecutive rows
  `clip = row . (world, 1)` whose last row is a unit vector and whose first two rows are perpendicular to it. Game clip space:
  y up, depth 0..1, infinite far (near plane about 2 units).
- **Shader:** `tools/mv-shaders/mv.comp` (`tools/make-mv-shader.sh` -> `mv_spv.h`). M = previous VP x inverse(current VP) (inverted
  in double precision on the CPU), applied to (ndc, depth, 1); y is flipped for Vulkan's top-left origin.
- **Check:** `KARTRECOMP_MV_DEBUG=1` paints the vectors over the 3D image (grey = still, red = right, green = down; 8 px
  saturates; the upscaler is skipped). In a race the ground flows outward and downward as expected, sky and HUD are clean.
- **Object motion (second layer), per 8x8 tile:** the camera vector is exact for the static world, wrong for anything that moves on
  its own (the player's kart, which follows the camera, other karts, items). Each pixel's camera vector is checked against last
  frame's luminance (`prev_luma`, an R8 image the same dispatch writes for the next frame; 5 taps, each a 2x2 box average, so
  texture aliasing isn't read as motion; the previous frame's jitter is compensated). A tile with at least 36 of 64 "bad" pixels
  searches last frame together (50 coarse candidates: a 5x5 grid around "didn't move" and one around the tile's camera vector, then
  a 1 px refinement), and its bad pixels take the winner. The winner must beat the camera vectors clearly, match well in absolute
  terms (< 0.06), differ by at least 2 px, and not be ambiguous (repeating road stripes match in several places: rejected).
  Everything else keeps the camera vector.
- **Jitter** is applied only to frames that have an upscale point and a game camera found last frame, so menu backgrounds with
  depth (title, character select) stay still. `KARTRECOMP_JITTER` / the overlay row still switch it on.
- **Cost:** a GPU timer around the pass logs "motion vectors: GPU x ms per frame" every 600 frames. 1080p race: about 0.03 ms
  for the camera layer alone, 0.1 ms with the per-pixel check, 0.3-0.4 ms with tile searches (about 2% of a 60 fps frame); menus
  0.02 ms. (The first per-pixel version cost 1.7 ms and made speckle on textures; the tiling, the blur and the ambiguity test fixed
  both.)
- **Cuts:** a camera turn of more than about 30 degrees or a jump of 150 units in one frame zeroes the vectors and sets `reset`.
- **Debug and tuning:** `KARTRECOMP_MV_DEBUG=1` paints the vectors (grey = still, red/green = right/down, 8 px saturates),
  `=2` paints only the object layer's corrections; `KARTRECOMP_MV_NOMATCH=1` turns the object layer off;
  `KARTRECOMP_MV_MINBAD=<n>` changes the tile trigger.
- **Tried and dropped:** marking the kart's draws (stencil written by the renderer). The draws before the game's first
  stencil-enabled draw include the road ahead and scenery, so the mask was far too wide; the game's draws carry nothing that
  identifies the kart. True per-object vectors would need each draw's previous transform (a second vertex pass), which the
  recompiled shaders don't offer.
- **Limits:** the kart is corrected on most but not all frames (partial coverage inside its silhouette); disocclusions behind a
  moving object have no vector; the match uses luminance, so flashing effects can fool it; tiles are 8x8, so vectors on object
  edges are blocky.

## FSR 3.1 plugin and the FSR 4.1.1 test (2026-10-21)

- **Plugin:** `plugins/fsr3/build.sh` fetches AMD's FidelityFX SDK v1.1.4 into `~/.cache/kartrecomp-fsr3`, ports its shader compiler to
  Linux, builds the FSR 3.1 upscaler and the Vulkan backend with a few local edits, and links our wrapper (`kr_upscaler_fsr3.cpp`) into
  `libkr_upscaler_fsr3.so`; copy that to `local/game/plugins/` and pick FSR 3.1 in the overlay (or `KARTRECOMP_UPSCALER=fsr3`).
  Nothing from the SDK is committed.
- **What the wrapper does:** allocates the three shared images FSR 3 needs (dilated depth, dilated motion, reconstructed previous
  depth), keeps its own RGBA16F output and converts it into the host's output image, returns every image to GENERAL after the dispatch,
  and wraps the device's function loader (some KHR/EXT names, debug-utils no-ops). The colour is passed as it comes (gamma-encoded): AMD's
  own 3.1.5 doesn't convert it either, and the output matches only without a conversion (`KARTRECOMP_FSR3_OPT=lin` for the experiment).
- **The bug that smeared everything:** on AMD GPUs FSR 3.1 picks a Lanczos look-up-table history filter, but the Vulkan backend of this
  SDK release never uploads the table's data, so the filter ran on zeros (blocky, over-smooth, trailing). `build.sh` turns the table path
  off (the shader's own approximation is used). Before: 32 dB against AMD's 3.1.5 output on the same inputs; after: 58.9 dB.
- **Reactive mask:** AMD's guidance for alpha-blended objects (particles, glass, boost flames), which have no motion vectors. The host
  copies the 3D scene colour aside before the first alpha-blended draw of the scene pass (`CaptureOpaqueColor`) and hands the plugin that
  copy and the finished scene colour (`KrUpscalerFrame::opaque_color`, `scene_color`); the plugin has FSR generate a reactive mask from the
  pair. `KARTRECOMP_FSR3_OPT=noreactive` turns it off. Other plugin switches: `KARTRECOMP_FSR3_OPT` (`lin`, `jflipx`, `jflipy`, `mvflipx`,
  `mvflipy`, `noinf`, `hdr`, `autoexp`, `jcancel`) and `KARTRECOMP_FSR3_PARAMS` (`vs2m`, `near`, `fov`, `rscale`, `rcutoff`, `rvalue`).
- **Jitter phases:** now 8 x (output / render)^2 (8 at 100%, 18 at 67%, 32 at 50%, capped at 72), FSR's recommendation.
- **Host fixes made on the way:** menu and loading frames (no game camera) are a plain upscale and the temporal history restarts at the next
  3D frame (the plugin used to return without writing, leaving stale output); the upscaler plugin is unloaded before the Vulkan device is
  destroyed (it crashed on exit); the plugin library is never dlclosed.
- **FSR 4.1.1:** AMD ships it only as signed DX12 DLLs (SDK 2.x says Vulkan isn't supported), so it can't be linked into this process.
  `tools/fsr4-test/` runs it under GE-Proton on frames the game dumped (`plugins/dump`), next to AMD's 3.1.5 and our plugin, same inputs.
  On a 120-frame race dump at 50% scale: edge energy bicubic 0.0226, ours 0.0183, AMD 3.1.5 0.0182, FSR 4.1.1 0.0200. FSR 4 is visibly
  cleaner on thin detail (the MKTV signs in the stands stay readable); it needs RDNA 3/4 and the DX12 path, so it is a quality yardstick here.
- **Motion vectors, round three:** object matching skips pixels farther than 1500 view units (the crowd keeps the exact camera vector),
  has a per-pixel refinement inside accepted tiles, and a GPU timer logs the cost (about 0.15 ms in a race at 1080p; `KARTRECOMP_MV_DEBUG`
  modes 1-4: vectors, object corrections, distance, reprojection error; `KARTRECOMP_MV_GAIN` scales the colours).

## Sharpening, supersampling, texture bursts (2026-10-21, later)

- **Sharpening row** (Off / Low / Medium / High, default High): a contrast-adaptive sharpen of the upscaled 3D image before the HUD
  (`tools/sharpen-shaders/sharpen.comp`, `SharpenUp`), for every upscaler alike (FSR 1 keeps its own RCAS; the FSR 3 plugin now gets
  sharpness 0 from the host). It has coring (tiny differences = texture grain are left alone, which removed the dotted artifacts) and a
  limiter (no overshoot past the neighbourhood).
- **Supersampling:** 3D render scale 150% and 200% (appended to the row so saved indexes keep their meaning): the scene is rendered
  larger and averaged down at the upscale point; no temporal upscaler, no jitter. 60 fps held in a 1440p test at both.
- **Shadow maps follow the resolution** (checked with `KARTRECOMP_DEPTH_LOG=1`): at 4K the 1024^2 cascades come out at 2048^2, 1536^2 at
  3072^2 and the 2048^2 map at 4096^2 (the same factor as the screen).
- **The race-load texture burst:** the first frame of a course wants about 600 textures (500 MB decoded). Taking them in one frame was a
  ~160 ms stall; now the frame takes about 20 ms worth (`KARTRECOMP_NATIVE_TEX_BUDGET_MS`, 0 = old behaviour), draws that need a waiting
  texture are skipped for those frames (not drawn white), and the rest is decoded in the background and created in the next frames
  (worst frame ~80 ms, mostly shader building, under the loading-screen fade). A background pre-decoder also decodes descriptors that
  appear in the pool early (a sample hash of the guest bytes guards against data that is still streaming in; `KARTRECOMP_NATIVE_NOPREDECODE=1`
  turns it off). Most of a course's textures are only registered on that first frame, so the pre-decoder helps less than hoped.

## Ghosting, reflections (2026-10-21, latest)

- **Reflections on the bike went dark** after the texture-burst spreading: the game renders its reflection probe once at the race start,
  and draws that waited for a texture were skipped, so the probe stayed empty. Now only draws into the main screen image can be skipped;
  off-screen passes create what they need at once. (The background pre-decoder is opt-in, `KARTRECOMP_NATIVE_PREDECODE=1`: a texture
  decoded early can be a stale copy of one the game is still filling in.)
- **DLAA ghosting:** the motion pass now also writes a "mismatch" mask (R8, 0..0.9: how little the camera vector explains this pixel; animated
  characters, effects) and the FSR 3 plugin gives FSR the larger of that and its own alpha-blend mask (`combine.comp`) as the reactive input;
  FSR's shading-change scale is 2 (SDK default 1). Switches: `KARTRECOMP_FSR3_OPT=nomismatch`, `noreactive`; `KARTRECOMP_FSR3_PARAMS` also takes
  `velocity`, `reactscale`, `shadescale`, `accumadd`, `mindisocc`. Offline loop: `plugins/dump` (now also dumps the mask) + `tools/fsr4-test/replay_host`
  + a ghost metric (output vs input in flat areas); the numeric differences were small, the visible effect is on in-place animations.

## HDR10 output, texture LOD, bloom (2026-10-21, latest)

- **HDR output** (overlay row, saved as `hdr`, `hdr_paper`, `hdr_peak`; enabled only when the surface offers A2B10G10R10 with
  the HDR10 ST 2084 colour space, which needs `VK_EXT_swapchain_colorspace`). The present step is a fragment pass
  (`tools/hdr-shaders/hdr.{vert,frag}`, `tools/make-hdr-shader.sh` -> `hdr_spv.h`) instead of a blit: sRGB -> linear, a steeper
  curve (gamma 1.25) and saturation 1.12 on everything, then a gentle highlight stretch (square root of peak/paper, wide ramp from
  30% brightness) on the 3D image only, then Rec.709 -> Rec.2020 and PQ. The 3D part is found by comparing the finished frame
  with `hdr_clean`, a copy of the upscaled image taken before the HUD. The stretch fades in and out over a few frames so
  menus and loading screens cannot flicker. The overlay's own shader PQ-encodes its colours at paper white. HDR forces the
  upscale point on (so the clean copy exists) even with the render scale off. Defaults: paper 150 nits, peak 400 (the user's
  monitor is HDR400). Phase 2 (replace the game's tonemap with the pre-tonemap scene) is not started.
- **Texture LOD:** `SceneLodBias()`: -1 per output resolution step above 1080p (1440p -1, 4K -2), plus log2(render ratio) (and
  -0.5 with jitter) when a temporal upscaler renders below the output. Applied only to *material* textures (`IsMaterialTexture`: 2D, at most 2048 px, RGBA8/sRGB/BC1-BC3, uploaded from guest memory). On every sampler it broke the lighting and shadows (user-confirmed by A/B with `KARTRECOMP_LOD_RES=0`): baked light-map atlases, shadow masks, normal maps and look-up tables are data and keep the game's own detail level. `KARTRECOMP_LOD_RES=0` turns the
  per-resolution part off.
- **Bloom:** the 480x272 bloom chain is a scalable target now (`KARTRECOMP_BLOOM_SCALE=0` to disable).

## Frame generation (2026-10-21, latest)

Overlay row "Frame generation" (`framegen` in the ini): Off / On (2x). Works only with a temporal upscaler (FSR 3.1 plugin), on frames
that have an upscale point and a game camera; menus, loading screens and the first frame after a camera cut present normally.

- Per game frame the host keeps two clean 3D images (`hdr_clean` = this frame's upscaled, sharpened 3D image before the HUD, and
  `fg_prev`, rotated by a swap in `CaptureHdrClean`).
- `GenerateInterp` (compute, `tools/fg-shaders/interp.comp`, `tools/make-fg-shader.sh` -> `fg_spv.h`) builds the frame half way
  between them: sample the current image at `uv - mv*(1-t)` and the previous at `uv + mv*t` (the motion vectors are the ones the
  upscaler uses: camera plus the object layer), pick the motion-compensated pair when it agrees at least as well as the unmoved pair
  (disocclusions fall back to a plain blend), then lay the current frame's HUD over it (where the finished frame differs from the
  clean 3D image). It also writes an R8 HUD mask for the HDR pass.
- Presenting: `Render` presents the generated frame first (in the main command buffer), sleeps until half a frame (a running
  average of the frame period) later, then presents the real frame from a second command buffer (`PresentRealFrame`, own fence and
  semaphores). The display therefore shows N-1, interpolated, N: half a frame of added latency.
- Measured on the scripted race: game fps 58.1 with it, 58.2 without (the extra cost is one compute pass and one more present).
- **Backends.** The overlay row lists Off, Built-in (the interpolator above) and every `plugins/libkr_framegen_<name>.so`. A backend
  exports `kr_framegen_get_api()` (`KrFrameGenApi` in `upscaler.h`, mirrored in `plugins/fsr3/kr_upscaler_abi.h`): it gets the previous
  and current HUD-less 3D images (output size, display-referred), the motion vectors and depth the upscaler used, jitter, camera
  near/fov and both view-projection matrices, a reset flag and `interpolation_t`, and writes an RGBA16F image; the host lays the HUD over it
  (`interp.comp`, mode 1), presents it, waits half a frame, presents the real frame. A backend that fails drops back to the built-in
  interpolator for the session. The ini key is `framegen=<off|builtin|name>`.
- **FSR 3 frame generation** is in the fsr3 plugin library (AMD's FfxOpticalflow + FfxFrameInterpolation from SDK v1.1.4, Vulkan
  backend): optical flow on the clean current image, then the interpolation with the upscaler's dilated depth / motion vectors /
  previous nearest depth (it shares them, so the library is loaded under both names: `build.sh` makes the `libkr_framegen_fsr3.so`
  symlink, keep it a symlink so the loader hands both names one mapping). `gen-ffx-shaders.sh` also generates the frame-interpolation
  and optical-flow shader blobs; the SDK files must be compiled with `-DFFX_FI=1 -DFFX_OF=1` or the shader-blob table is empty and the
  driver crashes creating the first optical-flow pipeline. Verified on the scripted race: the generated frame sits half way between the
  real ones, game fps unchanged.
- **FSR 4 / DLSS 4 frame generation:** not implemented, but they fit the same ABI. FSR 4 frame generation (AMD's SDK 2.x) is DX12-only
  with signed DLLs, so like the FSR 4.1.1 upscaler test it can only run offline through Proton; DLSS 4 (multi frame generation) needs an
  NVIDIA GPU and NVIDIA's Streamline/NGX, which hooks the swapchain (the host presents its own images, so a Streamline backend would
  have to take the generated image through its tagged-resource API instead). This machine has an AMD RX 9070, so neither can be tested
  here; the ABI carries what they ask for (depth, motion vectors, HUD-less colour, camera matrices, jitter).

## GPU cost, time-trial clock (2026-10-21, latest)

- `GPU frame time` log line (every 600 race frames): scripted race at 1440p on the RX 9070. FSR 3 at 100% (DLAA): 3.4-3.5 ms (scene 1.4-1.5, upscale + motion vectors + sharpening 1.9-2.0, HUD/present 0.1); FSR 3 at 67%: 2.4-2.6 ms; with HDR and the built-in frame generation 2.6-2.7 ms. The GPU is nowhere near the 16.7 ms budget, so the in-game frame drops are CPU-side (the recompiled game), not renderer-bound; GPU-side AMD/Mesa features (async compute, graphics pipeline libraries, ReBAR upload ring) would not change fps.
- Time-trial clock: `KARTRECOMP_HITCH=<period>,<ms>[,<from frame>]` sleeps in the renderer. A `--time-trial` TAS run with a 120 ms hitch every 30 frames from frame 2000 reads the same race timer at the same frame numbers as the clean run (3-10 ms apart; one 51 ms outlier from load alignment), so the race clock is frame-based and hitches cannot change time-trial results. `tools/make-menu-tas.py --time-trial` picks Time Trials (Down at frame 615).
